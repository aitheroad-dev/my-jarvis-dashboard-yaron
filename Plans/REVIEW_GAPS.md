# Architecture Review — Gaps & Risks

> Reviewer: PAI. Date: 2026-05-21.
> Goal: surface load-bearing cracks before any code ships. Yaron's directive: "very, very good architecture and very solid build."

## Tier 1 — Resolve before building (load-bearing cracks)

### 1. SSE → LISTEN/NOTIFY is broken for this stack

**The claim:** `AGENT_ARCHITECT.md §2.5` and §4.2 specify SSE backed by Postgres `LISTEN events` for real-time push. §8.2 flags the LISTEN/Neon-pooled question as "the single biggest open technical question" and recommends a spike before committing.

**Verified state:** `functions/_lib/db.ts:1` imports `neon` from `@neondatabase/serverless`. That's the **HTTP-over-Postgres serverless driver** — every query is a discrete HTTPS request to Neon's HTTP endpoint. There is no persistent TCP connection to attach a `LISTEN` to. The driver has no `LISTEN` API. The pgBouncer-transaction-mode question is moot; LISTEN/NOTIFY isn't on the table at all with this driver.

**Impact:** the entire push pipeline as drawn doesn't work. Without LISTEN/NOTIFY, the SSE endpoint can't be reactive to inserts. Falling back to "Pages Function polls Neon every 2s" (the architect's stated fallback) means: (a) Pages Functions consume their CPU budget polling, (b) Neon write costs go up, (c) actual latency is up to 2s per event regardless of how fast ingestion is.

**Resolution options:**

- **Option 1 — Use the WebSocket driver (`@neondatabase/serverless` *also* exposes a `Pool` over WebSockets that supports persistent connections, including LISTEN/NOTIFY).** This works in Cloudflare Workers/Pages Functions. Requires switching the SSE endpoint specifically to the Pool API, while keeping the rest of the codebase on the HTTP driver. Verification spike: ~2 hours. The architect's design then works as drawn.
- **Option 2 — Ingest endpoint emits to a separate channel.** Instead of writing to Neon and relying on LISTEN, the `POST /api/ingest/event` Pages Function ALSO writes to a **Durable Object** (one per tenant) that holds the SSE subscriber list and broadcasts directly. Neon becomes the durable store; the DO is the realtime fan-out. Matches the existing voice-channel DO pattern (`my-jarvis-voice-channel`). More moving parts, but no driver-level uncertainty.
- **Option 3 — Use a managed pub/sub (e.g., Upstash Redis, Cloudflare Queues).** Adds a SaaS dependency. Rejected unless 1 and 2 both fail.

**Recommendation:** **Option 1 first** — switch the SSE endpoint to the Pool-over-WebSocket driver. Spike it: stand up a minimal Pages Function that opens a Pool, executes `LISTEN events`, holds the connection. If it works in Pages Functions runtime, design is unchanged. If it fails (CPU limit, connection limit, or driver quirk), fall to Option 2 (DO fan-out) before any production code lands.

**Severity:** **CRITICAL.** Cannot ship Phase 1 until this is resolved.

### 2. No idempotency at ingest — duplicates or losses on restart

**The claim:** `AGENT_ARCHITECT.md §2.5` describes the Pulse forwarder using a checkpoint file (`MEMORY/STATE/dashboard-forwarder.json`) to resume after restart. §3.1 defines the `events` table with `id uuid PRIMARY KEY DEFAULT gen_random_uuid()` — server-generated id.

**The gap:** the client (forwarder) cannot enforce idempotency because it doesn't supply the id. The only way to dedupe is to check `(source, occurred_at, type, payload_hash)` — and there's no unique constraint on that tuple. On forwarder restart, two failure modes:

- **If checkpoint was written before successful POST:** events between checkpoint and last-actually-sent are skipped → silent data loss.
- **If checkpoint was written after successful POST but POST happened twice (network retry):** duplicates land in the events table → dashboard shows the same event twice.

**Impact on solidity:** the dashboard cannot be authoritative if its data is duplicated or partial. This is a "I don't trust the dashboard" failure mode, which is exactly what the solidity bar is meant to prevent.

**Resolution:**

- **Client-supplied dedup key.** Each event gets an `event_uid` generated by the source (e.g., `${source}:${occurred_at}:${sha256(payload)}`). The ingest endpoint UPSERTs on `event_uid` with `ON CONFLICT DO NOTHING`. Restarts become safe — replays are idempotent.
- **Add schema:** `events.event_uid text NOT NULL UNIQUE` (or composite UNIQUE on `(source, event_uid)`).
- **Checkpoint correctly:** write checkpoint AFTER successful POST + 2xx response, never before. Use an atomic rename pattern to avoid partial writes.

**Severity:** **CRITICAL.** Without this, the dashboard data integrity story is broken.

### 3. Initial sync (backfill) is unaddressed — 72+ existing artifacts on disk

**The claim:** `AGENT_ARCHITECT.md §9 Phase 2` describes Artifacts. Phase 1 only adds new events going forward.

**The gap:** there are already substantial artifacts on disk that need to land in the dashboard for the "single window" promise to hold from day one:

- `~/.claude/PAI/MEMORY/**/*.md` — **72 files** (verified via `find`)
- `~/Projects/**/Plans/**/*.md` — **9 files** (verified)
- Existing project, ticket, KB content already in Neon from the template seed
- Existing voice events in `MEMORY/VOICE/voice-events.jsonl`

If Phase 1 ships and Yaron opens the dashboard, the Artifacts page is empty. Every existing doc he might want is missing. He immediately reverts to Finder. The continuity principle breaks before it's tested.

**Resolution:**

- **Add a "bootstrap" step in Phase 2:** before turning on the live forwarder for artifacts, run a one-shot walker that reads every allowlisted path and POSTs to `/api/ingest/artifact`. With idempotency in place (Tier 1 #2), it's safe to re-run.
- **Backfill voice and events similarly** — one-shot replay of `MEMORY/VOICE/voice-events.jsonl` and `MEMORY/OBSERVABILITY/*.jsonl` into the dashboard at first run.
- **Surface progress:** dashboard shows "syncing initial 72 artifacts…" on first open. Yaron sees the work happening.

**Severity:** **HIGH.** Not a code-correctness bug — a UX bug that makes the dashboard unusable on launch.

### 4. Pulse-as-forwarder is a single point of failure for the dashboard

**The claim:** `AGENT_ARCHITECT.md §2.5` makes Pulse the forwarder agent. §8.1 acknowledges the risk: "Pulse is a single Bun process with a lot of responsibilities… restarts occasionally during PAI work." Recommends "if dashboard lag exceeds 60s more than once a week for two consecutive weeks, fork the forwarder."

**The gap:** the mitigation is reactive, not preventive. Yaron explicitly said "very, very solid." Coupling dashboard freshness to a daemon that's known to restart during PAI work is the opposite of solid. The architect's own §2.4 critique of pipe C ("Pulse becomes a SPOF") applies here — putting the forwarder *inside* Pulse, even framed as "Pulse is the agent, not the transport," still makes Pulse's process health into the dashboard's process health.

**Resolution:**

- **Ship the forwarder as its own launchd plist from day one.** A 200-line Bun script that does ONE thing: tail JSONL files, POST to dashboard ingest, manage checkpoint. Lifecycle managed by launchd directly. Crashes restart in seconds. Pulse remains the aggregator/UI layer but doesn't own the dashboard pipe.
- **Location:** `~/.claude/PAI/TOOLS/DashboardForwarder/` (alongside `PaiVoice/`). Plist at `~/Library/LaunchAgents/com.yaron.dashboard-forwarder.plist`.
- **Observability:** the forwarder writes its own `last_post_at` to a small status file; dashboard's `GET /api/sync/health` queries this via a separate read-only path *or* the forwarder POSTs its own heartbeat to dashboard every 10s. The dashboard top-bar status dot reflects forwarder health, not just lag.

**Severity:** **HIGH.** This is the difference between "solid" and "good enough." Yaron asked for solid.

## Tier 2 — Important; can resolve during build, not blockers

### 5. Edit-in-place protects against git overwrites, but most critical files aren't in git

**The claim:** §8.6 mandates `git status` check before writing. Refuses if uncommitted changes exist.

**The gap:** the most-edited PAI artifacts live in `~/.claude/PAI/MEMORY/**/*.md` — most of these are NOT in git (the live `~/.claude/` dir isn't a clean tracked tree). So the git-aware safety doesn't protect them. A dashboard edit can overwrite a memory file Yaron just updated in a terminal editor, without any check.

**Resolution:**

- Two-tier safety: (a) git check for git-tracked files (existing design), (b) **mtime + content_hash check for non-git files** — refuse to write if disk has been touched since dashboard's last `source_mtime`. Same conflict UI either way.
- Configure the allowlist to declare "git-required" vs "mtime-checked" per path prefix.

**Severity:** **HIGH** for solidity, but resolvable inside Phase 5 (edit-in-place).

---

### 6. `events` table grows forever — no retention design

**The claim:** §8.8 says "How many events/day does PAI produce? Order-of-magnitude estimate: 500-2000. The schema and SSE design handle 10x that without strain."

**The gap:** at 2000/day × 365 = 730k rows/year. The `payload jsonb` averages a few KB. That's a few GB/year *just for the activity log*. No archival, partitioning, or summarization story. Neon storage costs aren't large, but query performance on the `events_occurred_idx` degrades on huge tables, and the rail backfill on reconnect (replay since last id) walks a lot of data.

**Resolution:**

- **Retention policy:** keep raw events for 90 days, then auto-roll into a `events_archive` table or summarize-and-drop. Cron in Pulse (or the forwarder daemon) handles it.
- **Partitioning:** range-partition by `occurred_at` (monthly) so old data can be dropped by partition rather than DELETE.

**Severity:** **MEDIUM.** Not urgent at single-user scale; ugly to retrofit if deferred more than 6 months.

---

### 7. `artifacts.body_md` duplicates disk content in Postgres

**The claim:** §3.2 stores the full markdown body and generated HTML in Postgres for fast render + tsvector search.

**The gap:** for a 100KB doc, that's 100KB+ per row, plus `body_html`, plus the generated `body_tsv`. At 500 artifacts, ~150MB. At 10k artifacts (years of work), ~3GB. The disk has the canonical copy. Multi-device READ needs the body in the cloud, so we can't just store metadata. But duplication is real.

**Resolution:**

- **Acceptable at single-user scale.** Document it as a known trade-off, not a flaw. Revisit if Neon storage cost becomes meaningful (>$5/mo for storage).
- Alternative if needed: store body in **R2** (cheap), keep only metadata + tsvector in Neon. Adds a fetch step but decouples storage from DB cost.

**Severity:** **LOW** for now; flag for the year-2 reckoning.

### 8. Multi-device read story is implicit, not designed

**The claim:** Cf Access user auth handles "Yaron's phone hits the dashboard." Multi-device works because the data is in the cloud.

**The gap:** the architect's design assumes the main machine is alive and forwarder is running for fresh data. What does Yaron see on his phone when:

- His Mac is asleep? Stale-but-current-as-of-sleep data. OK — the top-bar status dot tells him this if it's working.
- His Mac was off for a week (vacation)? An entire week of activity is missing because the JSONL events from the local machine never made it to the cloud. The forwarder catches up *on wake*. The phone has no idea this is happening.
- He edits an artifact from his phone (Phase 5)? The local sync agent on his Mac is asleep. The edit lands in Neon but never on disk. Conflict the next time the Mac wakes if Yaron also edited locally.

**Resolution:**

- **Phase 1-3:** explicit "data captured locally" model. Document on the dashboard ("data current as of $LAST_LOCAL_SYNC"). Yaron knows.
- **Phase 5:** edits from non-main devices queue in Neon, applied to disk when local sync agent reconnects. Conflict resolution gets harder. May need to defer phone-editing to Phase 6 or 7.

**Severity:** **MEDIUM.** Affects UX clarity, not data correctness — but it shapes the trust contract.

## Tier 3 — Cleanup; resolve as they come up

### 9. Service token rotation has no design

**Gap:** §2.6 stores tokens in `~/.claude/.env`. No rotation cadence, no kill-switch. If the file leaks, attacker has write access to dashboard data.

**Resolution:** Cf Access service tokens are rotatable via dashboard or API. Document a quarterly rotation routine. For now, scope-restrict to write-only on ingest endpoints (already in the design).

### 10. Voice upload-to-R2 — who does it?

**Gap:** §6.1 says "either `say_local.py` extends to upload, OR Pulse uploads after the file is created." Unresolved.

**Resolution:** the new dashboard-forwarder daemon (per Tier 1 #4) owns this. When it sees a `voice.spoken` event with a local audio path in the payload, it uploads to R2 and replaces the path before POSTing.

### 11. `events.payload jsonb` has no schema validation

**Gap:** future hooks could emit malformed payloads. No validator at ingest.

**Resolution:** define a Zod schema per `(source, type)` pair. Validate in the Pages Function before insert. Log validation failures to a separate `ingest_errors` table.

### 12. FKs use slug, not id — slug renames break links

**Gap:** `events.project_slug REFERENCES projects(slug)`. If a project is renamed, the FK breaks (or in `ON DELETE SET NULL`, the link silently disappears).

**Resolution:** FK to `projects.id` (uuid) instead. Add a denormalized `project_slug` column for query convenience. Migrate when convenient.

### 13. SSE through Cf Pages Functions still needs a real-world test

**Gap:** §5.3 describes the SSE design but acknowledges (§8.4) that long-lived connections may behave unexpectedly under tab-throttling, OS sleep, etc.

**Resolution:** Phase 1's "end-state test" should explicitly include a 4-hour idle test — open the dashboard, leave the tab open and unfocused, return, check connection state. Real-world behavior, not just protocol correctness.

## What's RIGHT in the architect's design (don't lose these)

To make sure the review is balanced — the architect made several calls that are clearly correct:

- **Cf Access service tokens over `X-MCP-Secret`** for the new ingest endpoints. Single auth boundary, native primitive.
- **Disk-as-canonical-for-content, DB-canonical-for-metadata.** This decision sequence avoids most edit-in-place horrors.
- **Significance flag + classification.** Without it, the rail is noise.
- **Hash + mtime conflict detection for edit-in-place.** Right primitive.
- **`back-pointer to origin` on every event** (session_id, agent, project, artifact id). Makes the dashboard navigable.
- **SSE over WebSocket.** One-way push is all we need; HTTP semantics simplify auth.
- **Forwarder checkpoint** (the *concept* is right; the *placement* in Pulse is the issue per Tier 1 #4).
- **Path allowlist for artifact discovery.** Tight by default, expandable. Correct framing.

## Bottom line

The architect's design is mostly right but has one fatal flaw (LISTEN/NOTIFY isn't available on this stack) and three solidity gaps (idempotency, backfill, Pulse coupling) that should be closed before code ships. After those four fixes, the design earns the "very, very solid" label Yaron asked for. The fix surface is small relative to the design surface — this is a sharpening pass, not a rewrite.
